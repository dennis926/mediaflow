# 技术债：E2E 测试与生产环境未隔离

- 记录日期：2026-09-19
- 关联：`docs/DESIGN-多租户生命周期.md` §12.6（事故记录）、`docs/RUNBOOK-purge演练.md`
- 等级：**高**（测试可以写生产数据 —— 这是一类会造成真实事故的结构性问题）

## 一、现状（事实）

| 项 | 现状 |
| --- | --- |
| 数据库 | E2E **直接连生产库** `mediaflow`（同一台 PostgreSQL，无独立测试库） |
| Redis | 同样共用生产 Redis（队列已用独立 stream/group 规避，但 `auth:*`、`ops:*` 等键仍在同一实例） |
| 测试账号/工作区 | 用完由 teardown 按前缀清理（`E2E*`、`e2e-*@example.com`），但**清理本身也依赖测试正常结束** |
| 破坏能力 | 测试具备完整的 API 权限（管理员令牌），包括归档/软删/删除工作区 |
| 防护 | 骨架内置隔离覆盖（mock AI、关闭 Worker、独立队列流）+ 2026-09-19 新增的"默认工作区必须 active"跑前硬检查 |

## 二、本次事故（2026-09-19）

| 时间 | 事件 |
| --- | --- |
| 12:21:29 | 新增的 E2E 用例「外部 owner 不能删除默认工作区」**真的删除了生产默认工作区**（状态被置为 `soft_deleted`，保留期 30 天，未触发清除） |
| 12:21–12:25 | 默认工作区的业务接口对该工作区返回 404（整套 E2E 大面积失败，暴露了问题） |
| 12:25 前后 | 立即 `UPDATE workspaces SET status='active', deleted_at=NULL, purge_after=NULL` 恢复；核对审计链完整、健康 200、数据基线未变 |
| 影响 | **无数据丢失**（软删只改状态）；窗口约 4 分钟；审计完整可追溯 |

**根因（两层）**：
1. **直接原因**：`POST /users` 会把新用户加入**调用者当前所在的工作区**。测试在默认工作区的作用域下创建了那个"外部用户"，于是他成了默认工作区的 owner —— 所谓"跨租户"根本不成立，DELETE 理所当然成功。
2. **结构性原因**：**测试可以写生产**。只要测试跑在生产库上，任何用例设计失误都会直接作用到真实数据；换个失误方式（例如误删内容、误改成员），后果可能更重且不可逆。

## 三、已做的缓解（不替代根治）

1. 跑前硬检查：默认工作区非 `active` 时，**所有**基于骨架的套件拒绝运行（`test/support/e2e-harness.ts` 的 `assertDefaultWorkspaceIsActive()`，实测 10 个套件全部拒绝 + 62 个用例跳过）。
2. 金丝雀断言：破坏性用例执行后核对默认工作区仍为 `active`；`afterAll` 安全网发现异常立即修回并打印告警。
3. 隔离覆盖：AI 固定 mock、Worker 关闭、发布队列使用独立 stream/group（避免生产 Worker 消费测试消息）。
4. 卫生规则（写入设计文档 §12.6）：破坏性用例只作用于本次创建的探针工作区；创建用户前先确认令牌作用域。
5. 分类讨论记录：`docs/DECISION-E2E隔离.md`（队列维度的隔离决策）。

## 四、根治方案（B0.9 容器化时必须完成）

**目标**：E2E 跑在与生产完全分开的 PostgreSQL + Redis 实例上，跑完销毁。

| 步骤 | 做法 |
| --- | --- |
| 1 | `docker-compose.e2e.yml`：临时 postgres（随机端口、临时卷）+ 临时 redis，容器名带随机后缀 |
| 2 | E2E 启动脚本：起容器 → 等就绪（healthcheck/pg_isready）→ 建库 → `pnpm migrate` + `pnpm seed` → 跑测试 → `down -v` 销毁卷 |
| 3 | 环境注入：E2E 进程的 `DB_HOST/DB_PORT/DB_NAME/REDIS_HOST/REDIS_PORT` 全部指向临时实例；**不再读取生产 `.env` 的 DB/Redis 配置** |
| 4 | 防呆：E2E 启动时打印目标库的 `host/port/database`，并断言 `database` 名称不等于生产库名（例如必须等于 `mediaflow_e2e`） |
| 5 | CI 同规则：`.github/workflows/ci.yml` 的 test job 使用 service containers 或 compose，绝不连生产 |
| 6 | 数据夹具：种子脚本提供可重复的最小数据集，用例不再依赖生产里已有的内容 |

## 五、验收标准（B0.9 完成时必须逐条出示证据）

1. **E2E 不再连接生产 DB**：E2E 进程的 `DB_NAME` 为独立测试库；测试期间生产库 `pg_stat_activity` 中**没有**来自测试的连接（用 `application_name` 或独立库名即可证明）。
2. **Redis 也不共用**：E2E 使用的 Redis 实例与生产不同（`INFO server` 的 run_id 不同），测试产生的 `auth:*`/`ops:*` 键不出现在生产实例。
3. **失败也能清理**：测试中途 kill 掉进程后，临时容器与卷仍能被"下次运行"或清理任务回收（不残留）。
4. **可重复**：连续跑两次 E2E，结果一致（无残留数据导致的漂移）。
5. **跑前硬检查保留**：即便在独立库里，默认工作区检查仍然保留（防止种子数据被改坏后继续跑）。

## 六、为什么不能推迟到阶段 B1

- 阶段 B1（真机联调）会引入**真实平台凭证与真实发布动作**，届时测试若仍连生产库，一次失误可能造成**真实的对外发布**或**真实客户数据丢失**（阶段 C 对外开放后更甚）。
- 容器化（B0.9）本来就要做，E2E 隔离只是它的一个新增交付项，边际成本很低；越晚做，既有的 E2E 用例越依赖"生产库里有这些数据"的隐含前提，迁移越痛。

## 8. 2026-09-21 追加证据：残留会被"崩溃的运行"漏掉，已加启动前清扫

**发现过程**：B0.4 第 4 步验收时核对生产库，发现 **76 条 E2E 上传的孤儿素材行**（组名 `E2E并发/跨区/上传边界`，71 条名字带 `e2e`，文件早已被清理，只剩数据库行）以及 11 个 `uploads/tmp` 残留文件、1 条指向已清除工作区的 `workspace.purge_completed` 通知。

**根因（新增的第二层）**：teardown 只在套件正常结束时执行；**运行被 kill/超时/崩溃时 teardown 不会执行**，于是"删文件的那一步"可能已跑过而"删行的那一步"没跑，或两者都没跑。历史上 09-19 的残留来自"清理逻辑尚未加入"时期，09-21 07:16–07:26 的残留来自被中断的运行。

**处置**
1. 已清理全部残留（清单存档 `/root/.hermes/workspace/b0_4_residue_media_rows.txt`），清理后 `media_assets = 0`、`uploads/tmp` 为空、孤儿通知 0；生产基线（工作区 1 / 内容 1 / 用户 2 / 任务 0）未变。
2. **harness 增加启动前清扫** `sweepStaleTestResidue()`：每个套件启动时，删除"特征名匹配 + 文件确已不存在"的素材孤儿行，以及超过 1 小时的 tmp 残留（只认测试特征名与孤儿状态，绝不动真实上传）。已用"植入假残留 → 跑套件 → 残留被清"验证 ✓。
3. 新增可复用清理脚本 `apps/api/scripts/cleanup-test-residue.mjs`（默认干跑，`--apply` 才删除），供任何一次中断运行后手工收尾。

**技术债状态**：本条不改变 B0.9 的结论——根因仍是"E2E 直接读写生产库与 Redis"，彻底方案仍是临时 PG + Redis（`docker-compose.e2e.yml`）。本次新增的清扫只是把"残留看不见"变成"残留会被看见并自动收拾"，不替代隔离。

## 9. 已解决（B0.9，2026-09-21）

**这条技术债已闭环**：E2E 不再读写生产数据库与 Redis。

| 要求 | 实现 | 证据 |
| --- | --- | --- |
| 临时 PG + Redis，跑完销毁 | `docker-compose.e2e.yml`（tmpfs 无持久卷，端口 55432/56379，不发布到公网） | 每轮结束都执行 `down -v`；日志明确"临时依赖已销毁" |
| E2E 不再读生产 DB 配置 | runner 显式设置 `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` 指向临时库 | `E2E 库：mediaflow_e2e@55432` |
| 断言库名 | runner **第 0 步**：目标库名/端口与生产相同就直接退出（不跑任何测试） | 代码内 `if (E2E_DB === productionDbName) fail(...)` |
| 生产库在 E2E 期间无测试连接 | 哨兵每 3 秒采样生产库，累计两件事：① 生产库里出现 E2E 特征数据；② 生产库的 `pg_stat_activity` 里出现 E2E 专用账号（`mediaflow_e2e`）的连接 | 三轮运行：采样 49/53/64 次，**命中 0** |
| Redis 实例隔离 | 对比两个 Redis 的 `run_id`，相同即失败 | `d1730a3d07a2…` vs `91d6d091ebf8…` |
| 失败也能清理 | 清理放在 `finally`，测试失败/异常同样销毁容器 | 早期一次失败运行后容器与网络均已删除 |
| 可重复运行 | 每轮从零建库（迁移 + 种子 + 补 E2E 账号） | 连续 3 轮全绿：113/113（19 文件） |

**顺带修掉的两个真实缺陷**（都由这次隔离暴露）：

1. **种子不建工作区成员行** → 全新安装的管理员登录直接 403「该账号未被加入任何可用工作区」；
   现 `ensureAdminMembership()` 幂等补齐（存量库同样生效）。
2. **部署层开关被忽略** → 数据库未初始化时运行时快照退回代码默认值，`PUBLISH_WORKER_ENABLED=false` 失效，
   导致容器化后 api 与 worker **双消费者**；现 `PublishWorker.enabled()` 把环境变量当硬闸门。
   同时把 `SettingsService.flat()` 改为逐键容错，单个键读取失败不再让整份配置退回默认值。
3. 另修：E2E 规格硬编码生产默认工作区 id（种子生成的 UUID 每次不同）→ 统一走 `harness.defaultWorkspaceId()`。
