# 决策记录：三阶段路线图（内部先行 + 并行打对外基础）

| 项 | 内容 |
| --- | --- |
| 决策日期 | 2026-09-16 提出，2026-09-19 复核 |
| 决策 | 分三阶段推进：**阶段 A 内部可用（1-2 周）→ 阶段 B 内部真实使用 + 并行开发对外能力（4-6 周）→ 阶段 C 对外 SaaS（8-12 周）** |
| 状态 | 生效中（阶段 A 收尾） |
| 影响 | 直接决定排期、验收标准与"哪些缺陷必须现在修" |

## 一、约束条件（决策的前提）

1. **个人开发者，无公司实体**：无法用微信/支付宝企业支付、无法申请部分以企业资质为前提的开放平台能力（如小红书发布 API 需企业认证）。
2. **当前用户 ≤ 10 人**（内部团队），真实痛点是"多账号内容分发与矩阵运营的效率"，而不是并发与规模。
3. **合规是硬约束**：微信公众号禁止 API 自动发布（运营规范 3.27）、AI 生成内容必须显式与隐式标识。
4. **未来可能对外**：因此数据模型从第一天就有 `tenant_id` / `workspace_id`，权限走能力矩阵而非硬编码角色。

## 二、三阶段的目标与范围

### 阶段 A：内部可用（1-2 周）

| 目标 | 验收标准 |
| --- | --- |
| 内部 10 人能用起来 | PC + H5 全流程可用：创建内容 → AI 多平台适配 → 审核 → 排期发布 → 数据回收 |
| 关键风险已封闭 | P1-1（审核闸门可绕过）、P1-2（权限变更不即时）、P2-3（上传打爆内存）、P1-5（密钥无专用加密主密钥）、P2-5（刷新令牌不可撤销）、P1-4（密钥文件权限）全部修复并有回归测试 |
| 出事能查能回滚 | 队列修剪/审核闸门/密钥轮换/部署回滚四份 RUNBOOK；备份 + 演练 |
| 上线前有门禁 | `scripts/preflight.sh` 断言 + `scripts/deploy.sh`（失败即拒绝启动）+ CI |

阶段 A 明确**不做**：多租户注册、计费、SaaS 运营后台、容器化、多活。

### 阶段 B：内部真实使用 + 并行对外基础（4-6 周）

| 方向 | 内容 |
| --- | --- |
| 内部 | 真实内容生产（每周一批），用真实数据暴露问题；补齐平台凭证与人工发布 SOP |
| 对外基础 | 工作区生命周期（创建/归档/删除）、成员变更即时生效的完整覆盖、租户级配额、计费与订阅模型、租户级密钥隔离、合规审计链（AI 标识全链路留痕）、容器化、完整 CI/CD |
| 技术债 | 角色单一数据源（现存 `user_roles` 与 `workspace_members.role_codes` 双写）、权限粒度细化、工作区删除接口 |

### 阶段 C：对外 SaaS 启动（8-12 周）

注册与登录（含第三方登录）、支付与开票、服务条款/隐私政策/数据处理协议、平台凭证的租户自助配置、SLO 与告警值班、数据导出与删除（合规）、成本核算与定价验证。

## 三、为什么"内部先行 + 并行打对外基础"

| 备选方案 | 为什么不选 |
| --- | --- |
| 直接做 SaaS | 无公司实体时支付/平台资质走不通；且没有真实内容生产验证，做出来的多租户很可能方向错 |
| 只做内部工具，不预留对外 | 后期改造成本极高（数据模型、权限、密钥隔离都要返工）；本项目从第一天就在表里带 `tenant_id`/`workspace_id`，正是为了避免这次返工 |
| 内部先行 + 并行打基础（**已选**） | 内部使用提供真实反馈，同时把"对外才需要"的底座（租户、权限、密钥隔离、审计）按不返工的方式建好；每阶段都有可交付、可验收的边界 |

## 四、阶段划分的判断标准（避免模糊）

- 一项需求只要**内部 10 人用不到**、且**不影响数据模型不返工**，就归到阶段 B/C（例如计费界面、注册页）。
- 一项需求如果**不动现在就要返工**（数据模型、密钥边界、权限模型），即使对外才用，也必须在阶段 A/B 早期做完。
- 涉及**生产数据安全**的缺陷（密钥、备份、闸门、权限）一律 P1，不得推迟——这是阶段 A 花大量精力在密钥轮换与演练上的原因。
